## 2. Описание предметной области

Трекер привычек предназначен для ведения списка повторяющихся действий и ежедневной фиксации их выполнения. Пользователь создаёт привычку, указывает название, описание, категорию, цвет и целевую частоту в неделю. Каждый день можно создать не более одной отметки для одной привычки. По истории отметок вычисляется количество выполнений и серия последовательных дней.

## 3. Схема базы данных

```text
User (1) ─── (N) Habit (1) ─── (N) HabitLog
 id PK           id PK              id PK
 username        owner_id FK        habit_id FK
 password_hash   name               log_date
 created_at      description        note
                 category           created_at
                 color              UNIQUE(habit_id, log_date)
                 target_per_week
                 is_active
                 created_at
```

- `users`: учётные записи и хеши паролей.
- `habits`: привычки, принадлежащие пользователю через `owner_id`.
- `habit_logs`: отметки по датам, связанные с привычкой через `habit_id`.
- Внешние ключи обеспечивают связи; уникальная пара `habit_id + log_date` запрещает дубли отметок за день.

## 4. Реализация

Backend реализован на FastAPI. Роутеры разделены на авторизацию и работу с привычками. SQLAlchemy 2.0 использует декларативные модели `Mapped` / `mapped_column`; запросы строятся через `select`, `func.count` и `group_by`. Таблицы создаются миграцией Alembic `0001_initial`.

Пароли хешируются алгоритмом scrypt с индивидуальной криптографически случайной солью. Авторизация основана на подписанной cookie `SessionMiddleware`; JWT не применяется. В сессии хранится идентификатор пользователя и CSRF-токен.

Frontend состоит из страниц регистрации, входа и основной страницы. Данные запрашиваются через `fetch`; динамические элементы списка создаются с помощью `createElement`, а пользовательские строки помещаются в `textContent`.

## 6. Безопасность

- Пароль в базе хранится только как scrypt-хеш с солью; поле `password_hash` отсутствует в схемах ответов API.
- Защищённые маршруты используют зависимость `get_current_user`.
- В запросах к привычкам применяется фильтр `owner_id == user.id`; при работе с отметками владелец проверяется через JOIN с `Habit`.
- `owner_id` никогда не принимается из тела запроса, а определяется по сессии.
- Пользовательский ввод отображается через `textContent`, не через `innerHTML`.
- Установлены CSP и защитные HTTP-заголовки; API-ответы запрещено кэшировать.
- Секретный ключ задаётся переменной окружения и не хранится в репозитории.
